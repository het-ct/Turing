Memory and storage management

Resource overview

According to “Turing Platform User Manual” 1.2.3, the on-chip resources of Het-X1 are as follows:

Het-X1 memory and storage capacity

resource

Capacity/configuration

use

On-chip SRAM

768 KB (288 KB exclusive to CPU, 480 KB exclusive to NPU)

Task stack, heap, DMA buffer and real-time data

On-chip PSRAM

QFN68 integrated 4 MB

UI frame buffer, audio and video cache and large temporary data

On-chip ROM

QFN32 integrated 4 MB

Boot code, firmware, or read-only resources

external storage

Supports SPI NAND Flash, SD NAND Flash and external SPI PSRAM

Firmware, file systems, models, and product resources

The actual available capacity depends on the chip package, boot reserved area, link script and product partition. It must be based on the map file of the target board before mass production.

Flash partitions and code snippets

Erase areas are aligned by 4 KB. The resident .com code is loaded from Flash into RAM and is suitable for interrupts and strict real-time paths; the on-demand .bank code resides in SPI ROM and has a load delay on the first call. It is forbidden to call the .bank function that has not been loaded in an interrupt; the string used by the ISR should also be placed in the .com area.

void __attribute__((section(".com_text"))) timer_isr(void)
{
    /* 仅执行有界的实时操作 */
}

Memory management methods

  1. Determine SRAM, PSRAM, ROM/Flash partitions and alignment boundaries in config.h and linker scripts.

  2. Estimate stack peaks for each task, reserving contiguous buffers for GUI, camera, audio, and DMA.

  3. Firmware, resources, file systems and OTA partitions do not overlap each other, and space and erase boundaries are verified before upgrading.

  4. Check the map file and app.dcf after compilation, and record the code, read-only data, heap and stack usage.

Things to note

  • DMA buffers must meet alignment, cache coherency, and lifetime requirements.

  • UI double buffering and model memory are put into PSRAM first, but bandwidth and worst-case frame time are evaluated.

  • The ISR, watchdog, and low-power wake paths use resident RAM code to avoid runtime loading.

  • The current project does not have a unified dynamic memory statistics API; heap water level, leak detection and defragmentation tools are to be developed.
