System security

security architecture

This section is organized based on 1.3 “X1 Security Architecture” of the “Turing Platform User Manual”. Security objectives include firmware confidentiality and integrity, device identity protection, secure storage of sensitive data, tamper resistance, and communications security. The security strategy should be designed as a whole from the startup chain, storage partition, key life cycle and mass production process, and cannot just add verification at the application layer.

Root of trust and firmware protection

X1 uses eFuse to save device-level keys and security configurations. BootROM/BootLoader performs signature verification on the firmware in Flash. The firmware can be stored encrypted using SPI_ENC_KEY and decrypted to RAM at runtime. Once written, an eFuse is generally irreversible and must be operated at a controlled production station.

Secure storage and tamper-proof

Sensitive data such as Wi-Fi passwords and user tokens should be encrypted and stored in the USER_DATA partition; bus scrambling can be enabled on the critical SPI Flash bus. The chip supports active tamper detection and can trigger key erasure when detecting events such as opening of the casing. The specific key management interface for secure storage CBB depends on the product solution; missing parts are to be developed.

Secure communications and privacy

The device certificate can be derived from DEVICE_SECRET and stored in the secure area; the network connection uses TLS/DTLS and performs server-side certificate verification. External communication avoids exposing the unique identifier of the chip, and user data such as logs, configurations, and sensor history are encrypted and anonymized according to product requirements.

Development and Release Check

  • Debugable images are retained during the development phase, and signing, encryption, and version verification are enabled for released images.

  • OTA must verify image integrity, signature, version and rollback status. See OTA upgrade。 for the process.

  • Do not write keys, tokens, and Wi-Fi passwords to normal logs or clear text configuration files.

  • eFuse burning, certificate injection, mass production recovery and security audit tools: To be developed.
