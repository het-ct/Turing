Coffee machine platform solution

The coffee machine case shows how to combine UI, sensors, actuators, algorithms, communication and exception handling into a complete product process. The page is not an isolated interface, but a visual entrance to the equipment state machine: user operations must be consistent with the waterway, temperature control, pressure and safety interlocking.

Permanent page

The resident layer can combine self-test, identity authentication, energy saving, time, weather, dynamic background, status icons and quick settings. State data is published uniformly by the business layer, and the page only subscribes to the normalized view model to prevent each control from directly reading the hardware.

Status update skeleton for resident pages
void coffee_home_update(const coffee_status_t *status)
{
    ui_set_temperature(status->water_temperature_c);
    ui_set_supply_level(COFFEE_SUPPLY_BEANS, status->bean_percent);
    ui_set_network_state(status->network_state);
    ui_set_alarm_visible(status->alarm_count != 0);
}

work page

The workflow can be broken down into roasting degree identification, programmable pressure control, precise temperature control, TDS adaptive extraction and milk foam control. Each step should define entry conditions, target values, timeouts, cancellability points, and failovers, rather than infer device status from progress animations.

User feedback

Reviews and taste memories should save “recipe version + actual process data + user ratings” rather than just recording the star rating. The next time you apply your preferences, you still need to tailor them to safety boundaries such as temperature, pressure, and material margin.

Exception handling

The exception page covers descaling/residue cleaning, adding beans/milk/water and guided troubleshooting. Error information should include: current impact, user-executable actions, device automatic processing status, and exit conditions. Faults involving heating, pressure, motor stalling or door cover interlocking must be entered into the safe state by the control layer first, and the UI cannot provide a continue button to bypass the protection.

Module layering

  • UI layer: pages, controls, animations, input events, and accessibility feedback.

  • Category CBB: Recipes, process orchestration, fault mapping, maintenance cycles and user preferences.

  • Capabilities CBB: Vision, audio, IMU, motor control, communications, logging and secure storage.

  • HAL/BSP: ADC, PWM, QDEC, GPIO, IIC, SPI, LCD and actual board-level device drivers.

The joint debugging sequence is recommended to start with a single sensor and actuator, then verify the closed-loop control, and finally access the UI and networking functions. Logs, timeouts and manual stop entries are retained at each step so that the level to which the system belongs can be quickly located when problems with the entire machine occur.
