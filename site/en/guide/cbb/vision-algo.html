Vision Algorithm Library

CBB Capability Components

Corresponding to camera capture, image 3A, Yolo, and other vision capabilities.

Overview

This module is aimed at image and vision algorithms. This page suggests collaboration between vision algorithm and camera engineers to supplement a complete description from data acquisition, preprocessing, algorithm models to deployment constraints.

Core capabilities

  • Camera Capture: Describe image input, resolution, frame rate, and buffer organization.

  • Image 3A: Describe auto-exposure, auto white balance, auto-focus, and other pipelines.

  • Yolo Algorithm: Describe the model, input format, inference process, and performance indicators.

Usage

Initialize the camera and frame buffer, perform cropping, format conversion, and inference according to the algorithm requirements, and then publish structured results.

  1. Prepare dependent HAL, board-level resources, and task/interrupt context.

  2. Create configuration and register state, data, or error callbacks.

  3. Start components and send input data or system events to the processing interface.

  4. Consume outputs in the business loop and handle timeouts, disconnections, and insufficient resources.

  5. Stop the data source, wait for asynchronous operations to complete, and then release component resources.

Example

The following code shows the access skeleton of the application adaptation layer. Function names are used to indicate responsibilities and should be replaced with the actual CBB interfaces provided in the project.

static void app_vision_event(const void *event)
{
    /* 将状态或处理结果投递到产品业务层。 */
    (void)event;
}

int app_vision_start(void)
{
    int ret = board_vision_prepare();
    if (ret != 0) return ret;

    ret = product_vision_init(app_vision_event);
    if (ret != 0) return ret;
    return product_vision_start();
}

int app_vision_process(const void *image_frame)
{
    if (image_frame == NULL) return -1;
    return product_vision_process(image_frame);
}

API reference

The current CBB page has not yet been associated with stable public header files. It is recommended that the specific implementation provide the following adaptation layer responsibilities, and switch to Doxygen automatic interface documentation once public header files are available.

Recommended Adaptation Layer Interfaces

Interface Responsibilities

Description

Call Constraints

init(config, callback)

Verify configuration, create context, and register event callbacks.

Each instance should be initialized only once.

start()

Start data sources, protocol state machines, or algorithm tasks.

Must be called after successful initialization.

process(input)

Input data frames or system events and produce results.

Clarify thread, interrupt, and buffer ownership.

set_callback(callback)

Register state, data, and error notifications.

Avoid blocking operations in callbacks.

stop() / deinit()

Stop asynchronous sources and release resources.

Stop first, then destroy the context.

Notes

  • Clearly define the sampling period, maximum delay, and buffer depth for real-time data links.

  • Error codes should retain underlying causes and let the product layer decide retry, downgrade, or reset strategies.

  • Do not release configurations, buffers, or user context while callbacks, DMA, and tasks are still running.

  • Dependencies between CBB and HAL should be concentrated in the adaptation layer to avoid business code directly accessing chip implementations.
