Storage, Logs, and

Persistent Data of OTA MCU Products typically include firmware, resources, configurations, calibration values, logs, and user historical data. Partitioning, erasure, encryption, and upgrade strategies need to be unified to avoid direct concatenation of addresses or file paths by the application layer.

Storage Responsibilities

  • : Firmware and resources: Placed according to link scripts and partition tables, erase regions must meet 4 KB alignment requirements.

  • Configuration and Calibration: Saves default values, version number, checksum, wear policies, and factory reset behavior.

  • Logs: Define levels, ring caches, power loss policies, and sensitive field desensitization rules.

  • Secure data: Use secure storage CBB; Wi-Fi passwords, tokens, and device secrets must not be written into regular logs.

OTA process

includes wireless connection, version reading, upgrade requests, firmware transfer, integrity verification, restart trial run, and image confirmation as a complete upgrade. State Machine, Interface Responsibilities, and Exception Checks See OTA update.

Release verification

  • covers power outages, network interruptions, insufficient space, incorrect signatures, low power, and duplicate downloads.

  • If the trial run fails, keep the old firmware bootable, confirm the new image, and then clean up the old data.

  • Records the compatibility of images, resources, configurations, and hardware versions.

  • Release packages are associated with signatures, build logs, and traceable version numbers.

Pixso

  • Currently, there is no unified OTA header file in the publicly available HAL; The het_ota_* interface in the manual still needs to be developed into a stable API, partition table, and mass production upgrade tools: To be developed.

  • Power-down protection file system and wear balancing strategy: To be developed.
