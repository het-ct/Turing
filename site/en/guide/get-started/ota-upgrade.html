OTA update

OTA strings together version discovery, image transfer, integrity verification, partition switching, and startup confirmation into a recoverable process. The basic sequence provided in the Turing platform manual is: wireless connection → read version → request upgrade → send firmware package → verify → restart.

Upgrade State Machine

  1. Pre-check: Confirm model, hardware version, battery level, free space, current partition, and target version.

  2. Download: Write in blocks to the inactive Flash partition or SD card, recording length and breakpoint information.

  3. Verify: Check the complete package hash, signature, image header, target address, and resource version.

  4. Trial Run: Mark the new image as temporary execution; after restart, complete peripheral and key service self-check.

  5. Confirmation: After self-check passes, confirm the current partition; in case of failure or watchdog reset, revert to the previous usable image.

Interface Responsibilities

The manual lists the following OTA interface roles, but these symbols do not appear in the current public HAL header files. Before integration, verify the OTA service header files and partition configuration for the SDK branch being used; do not declare functions directly by name.

OTA Interface Roles

Interface

Responsibility

het_ota_get_current_partition

Query the currently running A/B partition

het_ota_start_download

Initiate firmware or resource download and select Flash/SD card target

het_ota_write_flash

Write OTA data by offset; the caller is responsible for boundaries, alignment, and error recovery

het_ota_temp_execute_partition

Set the partition for the next temporary execution

het_ota_accept_image

Accept the new image validated through the trial run

het_ota_confirm_update_partition

Finally confirm the partition for stable operation

Application Skeleton

Application state machine adapted to the specific OTA service
int app_ota_install(const struct ota_manifest *manifest)
{
    int ret;

    ret = ota_precheck(manifest);
    if (ret != 0) {
        return ret;
    }

    ret = ota_download_to_inactive_partition(manifest);
    if (ret != 0) {
        return ret;
    }

    ret = ota_verify_image(manifest);
    if (ret != 0) {
        ota_discard_candidate();
        return ret;
    }

    ota_mark_trial_boot();
    return ota_reboot();
}

Pre-release Verification

  • Simulate power-off at the image header, body, and last data block respectively to confirm that the old version can still start.

  • Handle corrupt overwrite packages, signature errors, insufficient space, low battery, network interruption, and repeated delivery.

  • Write the compatibility relationship between the resource package and the firmware into the manifest to prevent reading incompatible resources after a firmware rollback.

  • During trial runs, confirm that there must be timeout and watchdog policies; the image cannot be unconditionally accepted immediately upon startup.

Warning

The current platform manual indicates that secure boot does not yet support hardware rollback protection based on version numbers. A/B partition recovery can only enhance availability and cannot prevent an attacker from installing a signed but older version of the image.
