Unified error code

File location: platform/common/het_err.h.

error model

The unified error type is het_err_t (int32_t). The return value must be interpreted in conjunction with the specific interface semantics: a negative value indicates an error, zero may indicate success, no data, or no progress, and a positive value usually indicates success or the length of the transfer. Event consumption results, status enumeration or length values ​​cannot be directly used as error codes.

coding layout

The error code is a signed structured value, including severity level, software level, module and detail fields:

Common mistakes

HET_ERR_FAIL, HET_ERR_NULL_PTR, HET_ERR_INVALID_PARAM, HET_ERR_NO_MEMORY, HET_ERR_TIMEOUT, HET_ERR_BUSY, HET_ERR_NOT_INIT, HET_ERR_NOT_SUPPORT, HET_ERR_IO, HET_ERR_CRC and HET_ERR_STATE are common basic errors. The peripheral module also defines subdivision errors related to instance, configuration, bus, transceiver and callback. The final meaning is based on the enumeration and macro definition in the corresponding header file.

Usage example

het_err_t ret = het_gpio_init(&cfg);
if (ret < 0) {
    /* 记录错误并执行降级或重试，不能继续使用未初始化的 GPIO */
    log_error("gpio init failed: %ld", (long)ret);
}

call constraints

  • The caller must check the return value and cannot use a fixed zero or negative value to judge all interfaces.

  • The original error is preserved when forwarding across layers; the module, instance, and operation phase are recorded when supplementary context is needed.

  • The interrupt context only returns non-blocking, ISR-usable errors and does not perform retries, log formatting, or dynamic allocation.

  • New error items should be updated simultaneously in the header file, tests, and this page; module error descriptions that are not currently covered are to be developed.
