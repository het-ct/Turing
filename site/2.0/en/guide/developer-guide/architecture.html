Software architecture and layering

Overview

Het-X1 uses a bottom-up layered design. Each layer only relies on the stable capabilities provided by the next layer. The upper layer uses the lower layer through interfaces and callbacks to prevent business code from directly accessing registers, chip startup code or specific device drivers. In this way, when the package, display device or RTOS is replaced, only the adaptation layer can be adjusted without rewriting the product business.

Hierarchical responsibilities

  • L1 Chip and SoC: Provides hardware resources such as CPU, storage, clock, interrupts and on-chip controller.

  • L2 peripheral HAL/BSP: Abstract GPIO, UART, IIC, SPI, LCD, timer and other hardware into a unified interface, and complete board-level pin, power and clock adaptation.

  • L3 OS/OSAL: Provides system services such as thread management, task communication, software timers, memory and critical sections, and isolates specific operating systems.

  • L4 middleware: Provides general capabilities such as GUI, file system, database, protocol stack, and sensor framework.

  • L5 CBB capability component: Encapsulates audio, Bluetooth, algorithms, logs, secure storage and other capabilities into composable modules.

  • L6 product application: complete the page, business state machine, device strategy and product configuration, without directly operating the underlying registers.

Boundaries and principles of responsibilities

The dependency direction is always L6 → L5 → L4 → L3 → L2 → L1. Cross-layer access should be completed through public header files, configuration items, or registered callbacks. Modules at the same level remain independent, and the creator explicitly manages resource ownership and lifecycles. Interrupt handlers only clear status and deliver sampling events; time-consuming processing belongs in tasks or main loops. For storage partition and code segment planning, see Memory and storage management; for board selection, see Board level configuration config.h.

OSAL boundaries

OSAL provides the upper layer with threads, queues, mutexes, software timers, heap allocation and critical section interfaces that are independent of the operating system; the lower layer is responsible for adapting specific schedulers, system beats, interrupts and memory implementations. The current repository does not yet provide a complete and unified OSAL porting package. The missing thread scheduler, queue backend and port adaptation are marked as to be developed. Applications must not bypass OSAL and directly rely on a certain RTOS native type.
