CANOpen communication library

CBB Capability Component

Corresponds to CANOpen master and slave capabilities.

Overview

This module is oriented to CANopen node communication. This page suggests supplementing content such as object dictionaries, PDO/SDO, network management, and device state machines.

core competencies

  • Master Station: Explains network management, device discovery and periodic data scheduling.

  • Slave: Description of object dictionary, status switching and event reporting.

  • Protocol Details: Explain core concepts and interfaces such as PDO / SDO / NMT.

How to use

Initialize the CAN bus, load the node ID and object dictionary, and process NMT, PDO, SDO and heartbeat events periodically.

  1. Prepare dependent HAL, board level resources and task/interrupt context.

  2. Create a configuration and register status, data, or error callbacks.

  3. Start the component and send input data or system events to the processing interface.

  4. Consume output in a business loop and handle timeouts, disconnections, and resource shortages.

  5. Stop the data source, wait for the asynchronous operation to end, and then release the component resources.

Usage example

The following code shows the access skeleton of the application adaptation layer. The function name is used to describe responsibilities and should be replaced by the CBB interface actually provided in the project.

static void app_canopen_event(const void *event)
{
    /* 将状态或处理结果投递到产品业务层。 */
    (void)event;
}

int app_canopen_start(void)
{
    int ret = board_canopen_prepare();
    if (ret != 0) return ret;

    ret = product_canopen_init(app_canopen_event);
    if (ret != 0) return ret;
    return product_canopen_start();
}

int app_canopen_process(const void *can_frame)
{
    if (can_frame == NULL) return -1;
    return product_canopen_process(can_frame);
}

API description

The current CBB page does not yet have a stable public header associated with it. It is recommended that the specific implementation provide the following adaptation layer responsibilities, and change them to Doxygen automatic interface description after the public header file is implemented.

Recommended adaptation layer interface

Interface responsibilities

illustrate

call constraints

init(config, callback)

Verify configuration, create context and register event callbacks.

Each instance is initialized only once.

start()

Start a data source, protocol state machine, or algorithm task.

Must be called after successful initialization.

process(input)

Input data frames or system events and produce results.

Clarify thread, interrupt and buffer ownership.

set_callback(callback)

Registration status, data and error notifications.

Avoid blocking operations in callbacks.

stop() / deinit()

Stop the asynchronous source and release the resource.

Stop first, then destroy the context.

Things to note

  • Explicit sampling period, maximum latency, and buffer depth for real-time data links.

  • The underlying cause of the error code should be retained, and the retry, downgrade, or reset strategy should be determined by the product layer.

  • Configuration, buffers, or user context must not be released while callbacks, DMAs, and tasks are still running.

  • The dependency between CBB and HAL should be concentrated on the adaptation layer to prevent business code from directly accessing the chip implementation.
